# Decision log

One entry per technical decision, newest at the bottom. Format: what was decided, the alternatives, why.

## 2026-09-17 — Python 3.12 managed by uv
Alternatives: system Python 3.9, Homebrew Python, conda. The Alpaca SDK requires 3.10+, so the system interpreter is out. uv installs and pins Python versions per project, creates the virtualenv, and resolves dependencies fast. Homebrew is still recommended to install uv itself.

## 2026-09-17 — alpaca-py as the only broker/data SDK
Alternatives: raw `requests` against the REST API, the deprecated `alpaca-trade-api`. alpaca-py is the maintained SDK (0.44.0, Aug 2026), typed with pydantic, and covers trading, data, screener and streaming. Raw REST is kept as a fallback in the API docs so the team can debug without the SDK.

## 2026-09-17 — REST snapshot polling for market data in v1
Alternatives: IEX websocket, historical bars endpoint polling. Free plan allows only 30 websocket symbols and withholds the last 15 minutes of SIP history. Multi-symbol snapshots with `feed=iex` return the latest trade and current minute bar for hundreds of symbols in one call, well within the 200/min budget.

## 2026-09-17 — Client-side exit logic with server-side safety stop
Alternatives: Alpaca native trailing stop. Native trailing stop cannot enforce a gain floor relative to entry. Client-side logic matches the brief exactly and is reusable in backtests. A plain stop-loss on the server covers the bot-crash case.

## 2026-09-17 — SQLite as the only datastore
Alternatives: Postgres, Parquet files, CSV. Single writer (bot), single reader (UI), small data volume, already installed. Parquet is the escape hatch for bars if needed.

## 2026-09-17 — Streamlit for the dashboard
Alternatives: FastAPI + React, Textual TUI, Dash. Streamlit needs no JavaScript toolchain and does tables and charts well. Runs as a separate process reading SQLite, so it cannot interfere with trading.

## 2026-09-17 — Strategy code is pure (no I/O)
So the same code runs in backtest and live, and so it can be unit tested with lists of bars.

## 2026-09-17 — Hard stop-loss added to the brief's rules
The brief only describes selling at a gain. Without a stop, a bad entry sits at a loss all day. Default 1% below entry, owner can change or disable.

## 2026-09-17 — Backtest fill model is slightly pessimistic
Nothing fills on the decision bar; limit buys need the next bar's low to reach the limit; stops fill at the open on a gap; slippage applied both ways. Paper trading is optimistic, so the backtester leans the other way to bracket reality.

## 2026-09-17 — Ledger and trades keyed by run_id
`daily_ledger` primary key is (run_id, date) and `trades` carries run_id + mode, so many backtests coexist with the live record in one database and the dashboard can show any of them.

## 2026-09-17 — Backtest peak tracking uses the bar high
Live, the bot sees ticks every 15 seconds and the peak reflects intra-minute highs. In replay only bars exist, so the peak is updated from each bar's high before the close is checked for an exit. Exits still fill on the next bar's open.

## 2026-09-17 — Ruff rule set
E, F, I, B, UP at line length 120. UP017 (datetime.UTC alias) ignored for readability.

## 2026-09-17 — Jev (TypeSafe) reserved for judgment, not strategy math
Jev returns calibrated probabilities for typed questions and cannot count, compare numbers or generate text. It will be used as a news / sentiment universe filter behind a `NewsSignal` interface with mock and null implementations, so the bot runs unchanged without a key. Raw answers are stored as features so thresholds can change without re-inference and the backtester can replay them. Owner is on the waitlist; the design and a verified API reference live in `.claude/skills/typesafe-jev/`.

## 2026-09-17 — Defaults moved to the sweep's best configuration; originals kept as a profile
Entry window 09:31 to 11:30 (was 09:40 to 15:00), streak 3 at 1.0% (was 5 at 0.5%), trail 1.5% with 0.5% floor (was 0.5% / 0.3%), max hold 60 min (was 120). Still a losing configuration (PF 0.91), adopted as the least-bad base for the entry-filter work. The original set is `config/profiles/v1-original.yaml`; the strategy doc has a parameter-history table.

## 2026-09-17 — Three entry filters adopted; volatility-scaled exits implemented but off
From a 446k-row feature dataset with a chronological train/test split, then confirmed in the replay engine: require SPY up >= 0.1% on the day, stock up <= 0.6% on the day, and streak trade-count ratio <= 0.7. PF 1.25 on 116 trades (SIP), 1.17 on IEX, positive on both halves. First profitable configuration; thin. Volatility-scaled exits gave PF 0.95 alone and 0.85 stacked on the filters, so they stay off. Pre-filter set kept as `config/profiles/v2-sweep-2026-09-17.yaml`.

## 2026-09-17 — Modelling protocol adopted from Dixon, Halperin & Bilokon
Before any classifier: run `scripts/diagnose_returns.py`. Validation is walk-forward by day with a verification slice; nothing is tuned on test days. Model ladder for ~8k rows: regularised logistic (reference is the three-gate rule), shallow trees, at most one tanh layer; no deep nets, RNNs or deep RL. Probabilities must be calibrated on the verification slice; claims of improvement need a Bayes factor or posterior, not a single split. Exits may be studied as optimal stopping on logged paths. Rationale and page references: `.claude/skills/dixon-ml-finance/`.

## 2026-09-17 — Streak trigger found non-predictive on 1-minute bars
Minute returns are white noise at lags 1–3; after the candidate trigger, forward return is −10.7 ± 9.2 bp at 60 minutes. The strategy's thin profit comes from the filters and the asymmetric exit. Next experiments target slower bars and pullback entries rather than trigger parameters. `docs/research/2026-09-17-streak-autocorrelation.md`.

## 2026-10-28 — Read Alpaca's asset list as raw JSON; retry dropped connections; alert on an empty universe
**Asset list.** On 2026-10-20 Alpaca began returning the exchange code `TXSE`, for the Texas Stock Exchange. alpaca-py 0.44.0, still the latest release, rejects any code missing from its list, so `get_all_assets` failed as a whole. Every universe build failed from then until 28 October. Alternatives: wait for an SDK release, which might be weeks away; patch the SDK's enum at import, which is fragile because pydantic builds its validators when the models are defined; or call the same endpoint through the SDK's own `get` and parse the JSON ourselves. We chose the last. It keeps the SDK's keys, paper host, timeouts and retries, and only drops the strict parsing (`data/assets.py`). Other SDK calls still parse strictly. That is acceptable where our filters keep TXSE stocks out. Revisit if alpaca-py adds TXSE.
**Retries.** alpaca-py retries only HTTP 429 and 504, and `requests` retries nothing. A urllib3 `Retry` is now mounted on each client's session. Connections that never opened are retried for every method. Dropped responses are retried for GET and HEAD only, so an order is never submitted twice.
**Universe recovery.** The start-up build gets three attempts, then a retry every 2 minutes while the universe is empty, instead of waiting for the 30-minute refresh. Symbols that arrive late get a warm-up. A recovery from empty also re-runs the strategies' session start.
**Alerts.** The health check now also alerts on an empty universe and on a skipped portfolio or options decision. Each slot records the day and reason of a skip in its heartbeat block.
**Not fixed in code: the Mac sleeps.** The power log shows the laptop on battery and asleep for most market hours in October. `caffeinate -i -s` cannot prevent sleep on battery or with the lid closed. That needs the owner: power, the `pmset` wake schedule, or an always-on machine.

## 2026-10-28 — A watchdog for restarts in trading hours; phone alerts through ntfy
**Watchdog.** launchd relaunches the bot after a crash but not after the Mac restarts, so a power cut mid-session left it down until the next morning. The operator tick (every five minutes) now starts the bot's launchd job when it is a weekday between 07:00 and 15:45 ET, the agent is loaded, no `run_bot.py` process exists, and the bot's last heartbeat is older than the Mac's boot time (`sysctl kern.boottime`). Comparing the heartbeat with the boot time is what tells a restart (start it) from the owner stopping the bot with `pkill` (the bot has run since the boot: leave it). It also prevents restart loops, because a started bot writes a heartbeat within seconds; as a second guard there is one attempt per boot. Alternatives: `RunAtLoad` on the bot agent would also start a bot at every login, on weekends and after the close, and could not tell a deliberate stop from a restart; `KeepAlive` true would undo every `pkill`. Every system call fails towards "do not start", and `launchctl kickstart` is used without `-k`, so it can never kill a running bot. `src/ridethewave/operator/watchdog.py`.
**Phone alerts.** On the Mac mini nobody sees a macOS banner. Chosen: ntfy (a free push service; an HTTPS POST to a topic the phone app subscribes to), with the topic kept in `.env` because anyone who knows it can read the alerts. Not iMessage: sending from a script means AppleScript control of Messages, which needs a macOS Automation permission, and that permission's prompt does not reliably appear for a job started by launchd, so the first alert could fail silently. Not email: it needs SMTP credentials (an app password) on the machine and is slower to notice. Pushover works the same way as ntfy but costs a one-off fee and needs an account. The macOS banner stays.

## 2026-10-29 — A sell never goes past the protective stop or past what the broker holds
On the first Mac mini session, Alpaca's protective stop sold NUWE six seconds before the bot's own hard-stop exit fired. The bot then sent a market sell for shares it no longer held; Alpaca refused only because NUWE could not be shorted. The two stops sit about 1% below entry, so this race will recur. Alternatives: drop the client-side hard stop and rely on the server stop alone; widen the server stop so it only covers a crashed bot; or check before selling. We chose to check before selling, and kept both stops, because each covers a different failure. After cancelling the stop, the bot reads its final state, waiting up to 2 s while it is `pending_cancel`. A filled stop is booked as the exit; a partly filled stop leaves only the rest to sell. Live slots also never sell more than Alpaca reports holding. That costs one positions call per exit, and exits are rare. It is the general guard against an accidental short. Shadow and backtest slots skip the holdings check, because their brokers are simulated.
Also corrected: the bot's launchd job (KeepAlive with SuccessfulExit false) implies RunAtLoad, so launchd restarts the bot at login after a reboot; the watchdog is a backup, not the only cover. The watchdog now calls system tools by full path, because the agents' PATH has no /usr/sbin.

## 2026-10-29 — An options close is priced from the best price available, never silently at entry
The shadow QQQ covered call closed a day before expiry with P&L $0.00, but the real figure was −$1,892.13. Its short call was quoted bid 0 / ask 0.02, and the shadow fill rule refused any leg without a bid. The fallback was the structure's last mark, which lived only in memory, and a restart the night before had wiped it. So the books took the entry value. Alternatives: refuse to close until both sides are quoted (it could then hold past expiry); or price every missing leg at zero (wrong for a short leg the slot must buy back). We chose to let a close use a one-sided quote, because buying back pays the ask and selling a bid-less option gets nothing. When even that fails, the books fall back in order: mid of whatever is quoted, the saved last mark, then exercise value at spot. The entry value is a logged error. Marks are now saved with the slot's cash. The record was re-priced the same evening, with a database backup kept next to the file. Backtests are unchanged, because their quotes never have an ask without a bid.

## 2026-10-29 — The watchdog also covers a morning start that never ran
The bot's only calendar job is its 06:30 ET weekday start. Before 30 October it had never started the bot on the Mac mini, because on 29 October the bot was already running from the previous evening's restart test. On the laptop, launchd once fired calendar jobs two hours late. If a start never came, nothing would have started the bot; the owner would have learned from the 09:00 report ("stopped") and the 09:30 stale-heartbeat alert. The start time is now one constant (`watchdog.SCHEDULED_START`), which `install_launchd.py` reads.

## 2026-11-02 — Risk budget for the combined book: 10% volatility a year, a 15% drawdown limit; selling options only with defined risk
The owner accepted the proposal without naming a drawdown figure, so these are Claude's defaults, open to change. 10% is a common target for a multi-strategy book: about 60% of the stock market's volatility. The 15% limit is a budget, not yet an automatic stop: a sleeve whose history breaches it at its own 10% target cannot be promoted without a smaller allocation. **Measured the same day (docs/research/2026-11-02-trend-following.md, section 6): the two numbers conflict for any book holding stock risk.** Over 1990-2026, every such combination at 10% volatility drew down 26% to 39% in 2000-02; staying inside 15% needed a target of about 4% to 6.5%. The owner has to choose which number gives way. Selling options is allowed only as structures with a bought wing (put spreads, covered calls), never naked, matching what Alpaca's level 3 accepts.

## 2026-11-02 — Trend following runs as an observation sleeve, judged as insurance, not as a return source
Over 2017-2026 the pre-registered long-short trend book earned the T-bill rate (Sharpe 0.00), and over a century trend on US stocks had a Sharpe of 0.37, against 0.45 for holding stocks. But it made money in the stock market's worst tenth of months in both samples, and in 1929-32, 1973-74, 1987, 2008-09, Q4 2018, Covid and 2022. It goes to shadow as `tf_etfs`. Whether it earns capital depends on how much it cuts the put-spread sleeve's crash losses (docs/research/2026-11-02-trend-following.md, section 6). Long-only trend was rejected for this job: it can only step aside in a sell-off, never profit from one.

## 2026-11-02 — The bull put spread is not promoted
The 36-year test of the `bps_spy` rule (docs/research/2026-11-02-put-spread-long-history.md) fails three of its four pre-registered criteria: 2.4% a year over T-bills (Sharpe 0.25, against 0.51 for the market), a −52% drawdown at the slot's 20% risk per spread, losses as deep as the market's in slow bear markets (2000-02: −49%). Its monthly correlation with stocks is 0.53, and adding it to constant-volatility stocks does not raise the Sharpe. Alternatives: promote anyway on the 2024-26 real-chain result (20 trades, one regime), or retire it now. It stays in shadow untouched until the owner decides between retiring it and observing it at 5% risk per spread, where its measured drawdown was −11.7%. `bps_qqq` runs the same rule and is expected to fail the same way.

## 2026-11-02 — Statistical arbitrage starts with a diagnostic, not an engine; momentum is scaled by its volatility
The owner wants to pursue stat arb as the most automatable approach. Ken French's century of data (docs/research/2026-11-02-momentum-and-reversal-century.md) shows its textbook base, short-term reversal on raw monthly returns, has earned nothing in large caps since 1977 and about 3 bp a trade since 2000, below our costs. So no engine is built yet. Stage 1 is a diagnostic of residual reversal over 1 to 5 days on our own point-in-time data, with next-open fills and a kill test; the engine (Ornstein-Uhlenbeck s-scores, Avellaneda and Lee 2010) comes only if it passes. Alternative: build the engine first (weeks of work that the century data says will most likely find nothing). The same study found momentum scaled by its own volatility passes the pre-set test (information ratio 0.83 over a century, 0.38 since 2000), so the next momentum step is that overlay on `pm_actives`. Also learned: Ken French's *daily* portfolio files re-sort every day; any series that includes yesterday's close carries the bid-ask bounce and is not a tradable return.

## 2026-11-02 — Always-on daily stat arb is stopped; the volatile-market version gets its own test; the momentum overlay goes to shadow
Stage 1 (docs/research/2026-11-02-statarb-stage1.md) failed its kill test, fixed in advance: residual reversal over 1 to 5 days in a point-in-time top 300 earns at most 17 bp per 5-day round trip, never t ≥ 2 in both halves, break-even 4.3 bp against our 5. ## 2026-11-09 — Trading costs are measured from quotes, and every simulated fill keeps its quote
